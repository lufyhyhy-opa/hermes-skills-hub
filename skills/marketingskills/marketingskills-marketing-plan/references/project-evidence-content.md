# Project evidence → executable content system

Use when a founder supplies portfolio, product, team and verification material to upgrade personal-brand or B2B content strategy.

## Ordered recipe
1. Read each source completely. Record its status, owner and section references. Create an override list from recorded answers: explicit later decision → still-valid earlier decision → specialist draft → previous strategy. Keep unresolved decisions open.
2. Build an inventory with: asset, audience problem, client/internal/prototype/product category, source section, contribution scope, currently observable public surface, test evidence, asset-use scope, measured result, missing evidence and owner. These fields are independent; a polished public site does not prove production operation or attribution.
3. Inspect permitted public pages without submitting customer forms or creating transactions. Preserve explicit prototype labels. Treat inaccessible pages as unverified rather than finding a route around private-network controls. Public observations update only publicly observable claims.
4. Select evidence-ready cases first. A client website can demonstrate catalogue structure or an enquiry journey without proving increased sales. Keep an untested warehouse product as research/demo backlog; keep internal media usage distinct from client outcomes. Never merge similarly named asset-generation, footage-editing and publishing systems by inference.
5. Derive a bounded topic matrix: topic label → problem → project → proposed demonstration → evidence required → CTA resource/readiness → responsible role → blocker. These are planning labels, not finished headlines/scripts or production approval.
6. Sequence slots within the actual founder/team time budget. Use a first-week checklist and phased roadmap; when a dependency fails, replace or defer a slot rather than inventing successful output. Link recent news to a case only when still timely and locally applicable.
7. Design the conversion path before inviting action: resource → suitability assessment → scoped audit → bounded implementation → acceptance → training/operation. Mark resources/forms as proposed until created and exercised. Do not fabricate audit results, free trials, service prices or promised outcomes.
8. Hand off a public-safe derivative with a change summary and source-by-file/section provenance. Exclude raw attachments and sensitive detail from both visible pages and downloadable/build assets. Cite internal filenames as provenance only, not publicly accessible links.

## Acceptance
- Every topic has a defensible scope and an evidence prerequisite.
- Unknown results remain unknown; old stars, user counts and test totals are not presented as current measurements.
- Product labels follow recorded decisions: invitation-only, trial, internal, prototype and available are not interchangeable.
- Team participation is assigned by role until public identity/asset permissions are established.
- Superseded calendars are visibly marked as baseline/archive, with a pointer to the current recommendation.
- Website publication and portfolio decisions do not complete per-content production gates.
